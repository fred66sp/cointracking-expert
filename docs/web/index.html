Qué es este proyecto

Un auditor, no un auxiliar. Primero reconcilia; después declara. Ese orden es la decisión de diseño más importante de todo el repositorio.

El producto es un agente de IA auditor que vive en Claude Code (ADR-006) y se apoya en una base de conocimiento propia. Su trabajo es revisar los datos de una cuenta de CoinTracking —accediendo por la API a través de un servidor MCP propio o por el CSV export— para detectar y explicar problemas: transferencias huérfanas, ventas sin base de coste, duplicados, saldos imposibles, incoherencias fiscales. Después guía al usuario paso a paso para corregirlos en la web de CoinTracking y, solo cuando los datos cuadran, prepara la información fiscal.

No es un SDK ni una librería de motores deterministas: eso se descartó explícitamente (ADR-006). El «producto» es el agente más su conocimiento especializado en auditoría, y por eso la calidad se mide en reconciliaciones correctas, no en líneas de código.

El recorrido completo, en cuatro pasos

proyectoAísla

Ningún trabajo ocurre sin proyecto activo: separa los datos de cada cuenta para que dos auditorías no se mezclen nunca (ADR-013).

datosObtiene

Dos vías: el MCP de la API (en vivo, solo lectura) o el CSV «Trade Table» exportado de CoinTracking.

auditoríaReconcilia

Coteja contra el exchange, la blockchain y el banco. Cada hallazgo se escribe como evidencia → causa → impacto → recomendación.

fiscalidadDeclara

Solo con la reconciliación cerrada: FIFO para el coste, tramos del año correspondiente y Modelo 721 si procede.

La regla mental. Un informe fiscal es tan bueno como la auditoría que lo precede. Si los datos no cuadran, la cifra no se da: se explica qué falta y qué hay que corregir primero.

Empezar

Tres cosas antes de la primera pasada: un proyecto activo, una fuente de datos y el CSV en la carpeta correcta.

1 · Fijar el proyecto activo

Cada proyecto tiene su carpeta de entrada y su carpeta de informes. El agente pregunta siempre con cuál se trabaja —aunque solo exista uno— y no adelanta contenido antes de la confirmación: podría no ser el proyecto que se quiere retomar.

USER_INPUT/
  agp/            # fuentes de un proyecto (CSV, capturas, extractos)
  otro-cliente/   # otro proyecto, aislado del anterior
reports/output/
  agp/            # informes generados para ese proyecto

2 · Elegir la vía de datos

VíaCuándo usarlaQué implica
MCP (API)Datos en vivo, consultas acotadas por fecha y agregados.Servidor propio en Go compilado; credenciales por variables de entorno, nunca en el repositorio; solo lectura.
CSV «Trade Table»Auditoría con el tool determinista, o cuando no hay API.Un export por cuenta; el agente valida el formato antes de interpretarlo (hay columnas «Cur.» repetidas: se parsea por posición).

3 · Ejecutar los chequeos deterministas

Antes de interpretar nada, la parte que puede calcularse se calcula con código, no con el modelo. Ese es el sentido del tool:

python tools/ct_audit.py USER_INPUT/<proyecto>/trades.csv
python tools/ct_audit.py USER_INPUT/<proyecto>/trades.csv --check negatives
python tools/ct_audit.py USER_INPUT/<proyecto>/trades.csv --check transfers --window-min 1440
python tools/ct_audit.py USER_INPUT/<proyecto>/trades.csv \
  --expect-balances '{"Binance":{"BTC":"0.5"}}'

La salida es un JSON con el formato detectado, el número de filas y el resultado de cada chequeo. Sobre esa base, el agente interpreta y explica; no al revés.

PREV
Lo que necesitas antes de empezarEl CSV de CoinTracking (o la clave de API), Python para el tool, y disciplina con la privacidad: los datos reales viven en USER_INPUT/ y reports/output/, excluidos de git.

Las seis fases de la auditoría

El orden no es estético: cada fase depende de que la anterior esté cerrada. Auditando duplicados sobre transferencias sin origen se pierde el tiempo.

FaseQué se revisaPeso orientativo
1 · Cobertura de fuentesQué cuentas, exchanges y wallets están importados y cuáles faltan.20 %
2 · DuplicadosOperaciones repetidas por doble importación (API + CSV) y falsos positivos por batching.25 %
3 · TransferenciasRetiradas sin depósito de destino y depósitos sin origen: fondos huérfanos.20 %
4 · Tipos y base de costeOperaciones mal clasificadas (staking como compra, convert como venta) y ventas sin coste.15 %
5 · Purchase poolCompras agotadas o asignadas en un orden que rompe el FIFO.10 %
6 · Cierre y documentaciónInforme con evidencia, cambios registrados y pendientes declarados.10 %

Cómo es un hallazgo

Todos los informes comparten la misma forma, y esa forma es lo que los hace auditables:

Evidencia   →   Causa   →   Impacto   →   Recomendación
Qué se ve       Por qué        Qué cuesta      Qué hacer, paso a paso
(en datos)      (mecanismo)    (fiscal/econ.)  (en la web de CoinTracking)

La recomendación se escribe para alguien que no domina CoinTracking: dónde hacer clic, qué campo rellenar y por qué. Cuando la corrección implica crear o editar una operación a mano, la explicación se cierra con un bloque-resumen copiable con los campos exactos (ADR-024).

Sin duplicar trabajo. Si en la misma conversación ya se auditó y después se pide la declaración, se reutiliza el resultado. Solo se re-audita si los datos cambiaron o cambió la fuente.

Caché y multi-proyecto

  • Caché por proyecto con política LRU y tiempo de vida: dos cuentas distintas nunca comparten entradas (ADR-016).
  • Credenciales fuera del repositorio: solo por variables de entorno o por fichero de entorno del proyecto. Existe un modo de credenciales por proyecto (--project-env-dir) para auditar dos cuentas diferentes sin contaminar la caché (ADR-040).
  • Solo lectura contra CoinTracking: el servidor no crea, edita ni borra operaciones. Las correcciones las aplica el usuario en la web, guiado.
  • Trazabilidad: cada llamada queda registrada con marca de tiempo y parámetros, lo que permite explicar de dónde sale cada cifra.
  • Procesos huérfanos en Windows: hay un ADR específico (ADR-0041) porque el problema apareció y no era obvio.

El detalle que más se olvida. Cuando el usuario corrige datos en CoinTracking, la caché queda obsoleta. Si no se invalida, las cifras nuevas se mezclan con las viejas: el error más caro posible en una auditoría.

Tres patas de vigencia (ADR-008 y ADR-022)

El conocimiento caduca, y caduca por tres motivos distintos que se revisan por separado:

Lo fiscal

Tramos, umbrales, criterios de la DGT y plazos cambian cada año. Nada se aplica «de memoria»: se reverifica contra AEAT, BOE o DGT.

Lo de CoinTracking

Formato CSV, tickers y herramientas cambian con la plataforma. La verdad del formato actual son los datos reales del usuario y el centro de ayuda oficial.

Lo regulatorio

Licencias, cierres y migraciones forzosas de exchanges (por ejemplo MiCA) afectan a la operativa y se comprueban antes de preparar una declaración.

Ante un hueco, no se rellena. El orden es siempre el mismo: buscar en knowledge/, si no está ir a la fuente oficial, y si sigue sin resolverse preguntar al usuario. Nunca inventar una regla fiscal: se marca [PENDIENTE DE FUNDAMENTAR].

El auditor determinista

La parte que puede calcularse se calcula con código. El modelo interpreta y explica; no hace aritmética de saldos en la cabeza.

tools/ct_audit.py es el código del repositorio que emite conclusiones sobre los datos del usuario, y por eso está vetado: sus chequeos son la referencia frente a la que se contrasta cualquier explicación. Se ejecuta sobre el CSV «Trade Table» y valida la cabecera antes de parsear, porque el export tiene columnas repetidas (Cur.) y solo la posición las distingue; si el formato no es una de las dos variantes verificadas (es_trade_table, en_full_export) falla en voz alta en lugar de adivinar.

ChequeoQué detectaPor qué importa
balancesReconstruye el saldo de cada activo por cuenta recorriendo todas las filas en orden.Es la prueba base: si el saldo reconstruido no cuadra con el exchange, algo falta o sobra.
negativesSaldos negativos imposibles en algún momento del histórico.Casi siempre significa importación incompleta, operación duplicada o fecha invertida.
transfersRetiradas sin depósito de destino y depósitos sin origen, con ventana configurable.Fondos que desaparecen o aparecen: rompen el coste y, con él, toda la fiscalidad.
duplicatesFilas exactamente iguales en todos los campos relevantes.El síntoma clásico de importar la API y el CSV a la vez.
collisionsUn mismo ticker usado para activos distintos.Dos monedas mezcladas en una sola serie destruyen el FIFO sin dejar rastro visible.
--expect-balancesCompara la reconstrucción con los saldos que declara el exchange.Convierte una sospecha en un descuadre concreto, activo por activo.

La salida está pensada para leerse en dos niveles: el agente interpreta los totales, y cuando hace falta el detalle se procesa con código en lugar de volcarlo en la conversación.

El límite, dicho sin rodeos. El tool calcula; el agente explica. Toda cantidad exacta es «estimación no vinculante» salvo que provenga de un cálculo determinista (ADR-006). Esta distinción no es un formalismo legal: es la razón por la que el proyecto puede ayudar sin prometer certezas que no puede dar.

Fiscalidad española

Tres piezas: qué se identifica (FIFO), en qué año tributa y con qué tipo; y un modelo informativo aparte para las tenencias en el extranjero.

Identificación de unidades: FIFO

Cada transmisión consume primero las unidades más antiguas del mismo activo. La identidad del activo es el ticker completo, y las colisiones de ticker del chequeo collisions existen precisamente porque dos monedas distintas bajo el mismo símbolo invalidan el cálculo. El coste no lo calcula el modelo: sale del informe de impuestos de CoinTracking, que es un cálculo determinista (ADR-006).

Permuta cripto-cripto

Cambiar una cripto por otra es una transmisión, no una operación neutra (art. 37.1.h LIRPF). Se valora en euros a la fecha de la operación, y la comisión forma parte de la valoración. Este es el error fiscal más común entre usuarios noveles: creer que «no vendí, solo cambié».

Tramos de la base del ahorro · ejercicio 2025

Base liquidableTipo aplicable
0 – 6.000 €19 %
6.000 – 50.000 €21 %
50.000 – 200.000 €23 %
200.000 – 300.000 €27 %
Más de 300.000 €30 %

El último tramo pasó del 28 % al 30 % en 2025. Los tipos se seleccionan por ejercicio: no se cablean en el código, porque cambian con la ley.

Compensación de pérdidas

  • Primero, con ganancias patrimoniales de la misma base del ahorro, sin límite.
  • Si queda saldo negativo, con el saldo positivo de rendimientos del capital mobiliario (intereses, staking…), con el límite del 25 % de ese saldo positivo —vigente desde 2018—.
  • Lo que aún sobrevive se arrastra a los cuatro ejercicios siguientes, en el mismo orden; pasado ese plazo, se pierde.
  • Existe además la regla anti-aplicación de pérdidas por recompra de valores homogéneos (art. 33.5.e y f LIRPF): vender con pérdida y recomprar en plazo no permite compensar esa pérdida todavía.

Modelo 721: criptomonedas en el extranjero

Quién está obligado

Quien tenga cripto en custodios no residentes cuyo valor conjunto a 31 de diciembre supere los 50.000 €. La autocustodia —control propio de las claves privadas, sea wallet hardware o software— queda fuera del modelo, con independencia del importe.

Plazo y continuidad

Del 1 de enero al 31 de marzo del año siguiente. Tras la primera presentación solo se repite si el saldo conjunto crece en más de 20.000 € respecto al que motivó la última declaración.

Los modelos 172, 173 y 721 son informativos y no tienen régimen sancionador propio: se aplica el general de la LGT (art. 198), con 20 € por dato y mínimos y máximos de 300 € y 20.000 €; la presentación voluntaria fuera de plazo reduce la cuantía a la mitad.

Nada de esto es asesoramiento fiscal. El agente identifica, clasifica y documenta; no presenta declaraciones ni emite cifras vinculantes. Cada dato fiscal de knowledge/taxation/ trae su fuente (AEAT, BOE, DGT) y su fecha de verificación, y se reverifica antes de aplicarlo a otro ejercicio.

La base de conocimiento se valida como si fuera código: tools/audit_mega_complete.py comprueba metadatos, identificadores y referencias; el hook de pre-commit y los flujos de integración continúa (audit-mega.yml para el conocimiento, go-tests.yml para el servidor MCP) impiden que un documento mal formado entre en la rama principal.

# validar antes de commitear
python tools/audit_mega_complete.py

# instalar la validación local (Windows)
powershell -ExecutionPolicy Bypass .\tools\install_hooks.ps1

Nada se publica sin permiso. El agente aplica cambios en los ficheros, pero nunca ejecuta git commit ni git push sin consentimiento explícito. La gobernanza protege al revisor: cambios pequeños, commits revisables y el porqué siempre escrito.

Trazabilidad, caché y memoria

Nada importante vive solo en el chat. Si no está en un informe, en el registro de cambios o en la memoria del proyecto, se puede perder.

Caché en disco

Los datos obtenidos se guardan en .cache/cointracking/ con marca de tiempo, excluidos de git. Se reutilizan mientras sean válidos y se invalidan en cuanto el usuario cambia algo en CoinTracking.

Registro de cambios

Toda corrección aplicada en CoinTracking se anota en reports/output/REGISTRO-CAMBIOS.md, solo añadiendo: qué se cambió, por qué, con qué evidencia, el antes y el después, y cómo se verificó.

Memoria de sesión

Al retomar en una sesión nueva se leen primero la memoria y los informes para recuperar el estado: qué cuentas están auditadas, cuáles pendientes y qué decisiones se tomaron.

Economía de tokens

  • Consultar lo mínimo: acotar por rango de fechas y límite, y preferir agregados antes que el detalle completo.
  • Procesar lo grande con código, no en el contexto: volcar a fichero y subir solo el resultado compacto.
  • No pegar volcados completos en la conversación ni en los informes: totales y ejemplos.
  • Verificar por lotes: guiar todas las correcciones de una ronda y comprobar una sola vez, al final, en lugar de consultar tras cada cambio.

Cómo se presenta un resultado

En la conversación, las listas de operaciones usan formatos compactos y consistentes según el caso —línea temporal, auditoría con marcas de verificación y avisos, balance por moneda, recorrido de fondos— (ADR-025). En disco, el informe sigue la plantilla de templates/AUDIT_REPORT.md.

Límites y principios

Un auditor que no dice sus límites no es un auditor. Estos son los del proyecto, y están escritos como decisiones, no como advertencias.

No es determinista

Es un modelo de lenguaje: encuentra y explica problemas cualitativos, pero no produce cifras fiscales vinculantes. Toda cantidad exacta es una estimación no vinculante salvo que provenga de un cálculo determinista.

Cero invención

Toda afirmación se apoya en los datos reales del usuario, la base de conocimiento fundamentada o una fuente oficial verificada en la sesión. Sin respaldo, no se afirma.

Ante la duda, para

Buscar en el conocimiento, luego en la fuente oficial, luego preguntar. Se prefiere «hay que verificar X» a una cifra dudosa, y el agente puede negarse a dar un número que no pueda fundamentar.

Consentimiento antes de actuar

Ante una acción consecuente —irreversible o con impacto fiscal— se explica qué se va a hacer, se advierte de la consecuencia de no hacerlo y se pregunta. No se aplica a lecturas ni a pasos triviales.

Lo que este agente no hace

  • No presenta declaraciones ni firma nada: prepara la información y la documenta.
  • No modifica CoinTracking por su cuenta: el servidor MCP es de solo lectura y las correcciones las aplica el usuario, guiado paso a paso.
  • No sustituye al profesional: el informe está pensado para que un asesor lo revise, con sus dudas declaradas.
  • No mezcla proyectos ni cuentas, ni siquiera cuando el nombre del archivo coincide.
  • No rellena huecos con supuestos plausibles: los marca como [VERIFICAR] o [PENDIENTE DE FUNDAMENTAR].
  • No oculta incertidumbre: el silencio no es aceptable, y lo que no se puede verificar se dice.

Preguntas cortas

Dudas que aparecen en las primeras sesiones, con la respuesta directa.

¿Dónde están mis datos?

En USER_INPUT/<proyecto>/ las fuentes que dejas; en reports/output/<proyecto>/ los informes; en .cache/cointracking/ las respuestas guardadas de la API. Las tres rutas están excluidas de git: nada de eso se versiona.

¿Puedo auditar dos cuentas distintas?

Sí, y deben ir en proyectos separados. El servidor MCP cambia de proyecto en caliente, y si cada cuenta tiene sus propias credenciales se arranca con --project-env-dir para que no compartan ni identidad ni caché (ADR-040).

¿El agente modifica mis operaciones en CoinTracking?

No. El servidor MCP solo lee. Lo que hace es detectar el problema, explicarlo y decirte exactamente qué cambiar en la web, campo a campo.

¿Necesito la API o me basta con el CSV?

Con el CSV basta para auditar y para usar el auditor determinista. La API añade datos en vivo y consultas agregadas, pero no es obligatoria.

¿Por qué aparecen duplicados si importé una sola vez?

Porque el CSV y la API pueden haberse importado en momentos distintos, o porque el exchange ejecutó varias operaciones en el mismo segundo. Antes de borrar nada se comprueba el Trade ID: si difiere, son legítimas (ADR-014).

¿Qué pasa si falta un exchange?

Se verá como transferencias huérfanas o saldos negativos. No se «arregla» a mano: el informe lo declara como fuente faltante y se importa el histórico antes de seguir, porque cualquier cifra calculada sin él sería falsa.

¿Por qué hay 42 ADR para un agente?

Porque el proyecto trata datos fiscales. Cada decisión que afecta a la corrección —cómo se detecta un duplicado, cuándo se invalida la caché, qué se puede afirmar— tiene que estar escrita y ser discutible. La alternativa es un agente que cambia de criterio sin que nadie lo note.

¿Qué significa «estimación no vinculante»?

Que la cifra sirve para entender, planificar y contrastar, pero no es una liquidación. Solo los cálculos deterministas —el tool y el informe de impuestos de CoinTracking— producen números que se pueden usar como base, y aun así los revisa un profesional.

¿Y si mis criptos están en una wallet propia?

Se auditan igual, pero no entran en el Modelo 721: la autocustodia queda fuera del modelo con independencia del importe, porque lo determinante es quién controla las claves privadas.

¿Cómo sabe el agente que he corregido algo en CoinTracking?

Porque se lo dices y porque la caché se invalida antes de volver a leer. Sin ese paso, las cifras nuevas se mezclarían con las viejas: es el error más caro posible en una auditoría.

¿Puedo usar solo una parte del sistema?

Sí. La base de conocimiento y el auditor determinista funcionan sin el servidor MCP; la skill de declaración necesita la reconciliación previa, aunque sea con el CSV.
